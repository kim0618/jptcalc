# /tistory-verify [번호들]

예: `/tistory-verify t7-t11`

순서: `/tistory`(작성) → **`/tistory-verify`(재검증)** → `/tistory-publish`(예약). 모든 단계는 Opus로 한다(11/20 사용자). 그래서 독립성은 모델을 바꾸는 대신 **작성 맥락이 없는 새 에이전트**로 만든다.

## 왜 따로 하나
작성한 세션이 같은 방법으로 다시 보면 같은 걸 놓친다. 11/19 경정청구 연도·부부 합계, 11/20 2월 29일생 나이를 쓴 직후가 아니라 나중에 잡았다. 검증자는 원고와 계산기·법령만 보고, 작성자의 계산이나 결론을 받지 않는다.

## 절차

### 1. 대상 확인
`~/jptcalc/tistory/queue.md`에서 대상이 "작성 완료(발행 대기)"인지 본다. `posts/tNNN-*.html`, `meta/tNNN.txt`가 있어야 한다.

### 2. 독립 검증 에이전트 (편마다 1개, 병렬)
Agent 도구(subagent_type: general-purpose)로 편마다 하나씩 띄운다. 프롬프트에는 **아래 템플릿만** 넣는다. 작성 때 뽑은 숫자, 큐의 축 설명, 내 판단은 넣지 않는다.

```
너는 블로그 원고 검증자다. 원고를 쓴 사람의 설명은 받지 않는다. 파일만 보고 독립적으로 확인한다. 원고 파일은 고치지 말고 결과만 보고한다.

원고: /home/tjd618/jptcalc/tistory/posts/<파일>
메타: /home/tjd618/jptcalc/tistory/meta/<tNNN>.txt (제목 포함)
계산기 원본: /home/tjd618/jptcalc/calc/<계산기 경로>/index.html (링크 URL의 /calc/ 뒤 경로)
도구:
- 계산기 함수 실행: cd /home/tjd618/jptcalc/tistory && LD_LIBRARY_PATH=$HOME/.local/emulib node run.mjs <calc 경로> <expr.js>  (expr.js 마지막 식이 JSON으로 출력됨. 페이지의 실제 함수를 그대로 부른다)
- 법령 원문: LD_LIBRARY_PATH=$HOME/.local/emulib node /home/tjd618/jptcalc/scripts/law-render.mjs <법령명> <출력경로>  → <출력경로>.txt 에서 조문 검색
- 그 밖에 python3로 직접 계산

할 일:
1. 제목·본문·표·캡처 설명에 나오는 숫자를 전부 뽑아, 하나씩 계산기 함수나 직접 계산으로 다시 구한다. 차이·합계·비율·연도·날짜·요일도 전부. 반올림 단위가 화면 표시와 같은지도 본다.
2. 법·제도·기관 기준에 관한 주장(공제율, 한도, 나이 기준, 시행일, 조문 번호, 판례 취지)을 원문으로 대조한다. 원문을 못 찾으면 "미확인"으로 적는다. 추측으로 맞다고 하지 않는다.
3. 일반화·단정 문장("대부분", "보통", "~하는 사람이 많다", "항상")에 근거가 있는지 본다. 근거 없으면 표시한다.
4. 계산기 화면 캡처 설명(회색 줄)의 숫자가 1번 결과와 맞는지 본다.

보고 형식(이것만):
- 틀림: 원문 문장 / 올바른 값 / 근거(계산식 또는 조문)
- 미확인: 원문 문장 / 왜 확인 못 했는지
- 과한 단정: 원문 문장 / 제안
- 확인 완료: 확인한 숫자·주장 개수
```

### 2-2. 문체·반복 패턴 검증 에이전트 (묶음당 1개, 2와 동시에)
숫자 검증과 별도로 하나 더 띄운다. 한 편씩 보면 반복이 안 보이므로 **이번 묶음 + 직전에 쓴 글 전부**를 나란히 읽게 한다. 역시 작성 의도·내 판단은 주지 않는다.

```
너는 블로그 원고의 문체 검증자다. 쓴 사람의 설명은 받지 않는다. 원고 파일은 고치지 말고 결과만 보고한다.

규칙: /home/tjd618/jptcalc/tistory/rules.md 의 §11(품질·AI 티·틀 반복) 을 먼저 읽는다.
이번 검증 대상: <대상 파일 목록>
비교 대상(이미 쓴 글): /home/tjd618/jptcalc/tistory/posts/ 안의 나머지 t*.html 전부
(본문 HTML에서 [[TOPIMG]]·[[CAPTURE1]]·스페이서 문단은 무시)

할 일:
1. AI가 쓴 티: 사람이 잘 안 쓰는 상투어·번역투·빈 강조·기계적 대칭(같은 길이 문단, 3개짜리 목록 반복, 모든 소제목 아래 같은 구조), 지나치게 매끈한 연결어, 근거 없는 공감 멘트를 문장 단위로 찾는다. 규칙의 금지어 목록에 없어도 어색하면 적는다.
2. 글끼리 반복: 대상 글과 비교 대상 글 사이에서 겹치는 것을 찾는다.
   - 도입 첫 2~3문장의 구조(예: "X면 Y예요. 그런데 Z" 꼴이 여러 편)
   - 소제목 패턴, 끝맺음 방식, 글쓴이 단락·기준 줄·CTA 문장의 틀
   - 자주 반복되는 문장 골격·어휘(예: "~이유입니다", "~셈이에요", "숫자로는 이 정도", "~라는 뜻이에요")를 편별 횟수와 함께
   - 문장 길이·리듬이 편마다 똑같은지
3. 독자가 "다른 블로그와 똑같다"고 느낄 지점(정보 나열만 있고 판단이 없는 구간 등).

보고 형식(이것만):
- AI 티: 파일 / 원문 문장 / 왜 / 고친 예
- 반복 패턴: 무엇이 / 어느 파일들에서(횟수) / 바꿀 방향
- 그대로 둬도 되는 것: 한 줄
- 전체 평가: 대상 글 각각 상·중·하와 이유 한 줄
```

### 3. 결과 처리 (메인 세션)
- **틀림**: 검증자의 근거를 내가 한 번 더 확인한 뒤(검증자도 틀릴 수 있다) 원고를 고친다. 숫자를 고치면 연결된 제목·meta TITLE/ALT·대표이미지(make_thumb)·캡처 설명·캡처 setup도 같이 고친다.
- **미확인**: 내가 원문을 찾아 확인한다. 못 찾으면 그 문장을 빼거나 "~로 안내돼 있어요"처럼 출처를 밝힌 표현으로 낮춘다.
- **과한 단정**: 근거가 없으면 고친다.
- **AI 티·반복 패턴**: 지적 문장을 다시 쓴다. 같은 틀이 여러 편이면 이번 묶음 쪽을 바꾼다(이미 발행된 글은 그대로). 글쓴이 단락·기준 줄·CTA처럼 매 편 들어가는 부분도 문장 틀을 돌려 쓴다. 고친 뒤 숫자가 바뀌지 않았는지 확인한다.
- **문체 수정에 새 사실을 넣지 않는다(11/24)**: 문체 지적을 고칠 때 새 숫자·법 조항·계산기 동작·일반화("~뿐", "보통", 새 예시)를 넣지 않는다. 꼭 넣어야 하면 그 자리에서 계산기·python3로 계산·실측하고, 3-2 최종 검증 대상이 된다.
- 고친 뒤 `python3 check_post.py posts/tNNN-*.html` + `node mobile_check.mjs posts/tNNN-*.html` 다시 PASS.

### 3-2. 최종 통합 검증 (11/24 필수, 0건이 나올 때까지)
고치면서 새로 쓴 문장(캡션·설명·이유)이 새 오류를 만든다(폼다 11/24 t16~t20: 캡션 "맨 끝 칸", 반올림 설명, 같은 날 입금, 비문, 결론과 이유 충돌). 숫자 고친 편만 다시 보는 방식으로는 못 잡는다. 그래서 **모든 수정이 끝난 최종본 묶음 전체**를 새 에이전트 1개가 다시 본다(6편 넘으면 6편씩 나눠 병렬). 기존 "숫자 고친 편만 재검증(최대 2회)·문체만 재검증(최대 2회)"은 이걸로 대체한다. 프롬프트는 아래 템플릿만 쓰고, 이전 검증 결과·고친 내용은 주지 않는다.

```
너는 블로그 원고 최종 검증자다. 쓴 사람·이전 검증의 설명은 받지 않는다. 원고 파일은 고치지 말고 결과만 보고한다.
원고: /home/tjd618/jptcalc/tistory/posts/<대상 파일들>
메타: /home/tjd618/jptcalc/tistory/meta/<tNNN>.txt (제목·ALT·EXAMPLE)

할 일(문장 하나씩): 1 법 조문·숫자·날짜·요일·금액 원문/계산 대조 2 계산기 서술·캡처 설명이 실제 페이지·캡처와 맞는지 3 앞뒤 일관성(예시 인물의 나이·기간·날짜 순서, 예시와 결론이 어긋나는지, 섹션 순서와 참조, 이유와 권고가 충돌하는지) 4 근거 없는 단정 5 비문·어색한 문장
```

- 지적이 나오면 직접 확인 → 고침 → **다시 3-2를 새 에이전트로**. "틀림·앞뒤 어긋남·비문" 0건이 나와야 검증 완료. 과한 단정은 고치거나 근거를 적는다.
- 최대 3회. 3회째에도 틀림이 나오면 예약하지 말고 사용자에게 남은 지적을 그대로 보고한다.
- 3-2 뒤에 원고를 한 글자라도 고치면 3-2를 다시 돌린다(사용자 지시로 고친 것 포함).

### 4. 기록·보고
- `queue.md` 상태 "검증 완료(발행 대기)"는 3-2가 0건일 때만.
- `ledger.tsv`는 건드리지 않는다(발행 때 기록).

- 사용자에게: 편별로 확인한 개수, 고친 것(전→후, 근거), 뺀 것, 미확인으로 남긴 것, 문체 평가(상·중·하)와 고친 반복 패턴. 이어서 `/tistory-publish`로 예약하면 된다고 안내.
